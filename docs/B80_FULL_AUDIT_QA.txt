ROOT CAUSE CONFIRMED
- PostgreSQL server was healthy while TCP/SCRAM authentication for role postgres failed repeatedly.
- Existing PGDATA may retain the role password set during its original initialization even if POSTGRES_PASSWORD is later changed in Compose.
- Previous deployment had no credential-reconciliation gate before migrations.

B80 BEHAVIOR
- No PostgreSQL data-volume deletion/recreation.
- Docker local/production self-hosted flow adds dbcredential before migrate.
- dbcredential uses the PostgreSQL Unix socket, rotates the postgres role to configured POSTGRES_PASSWORD, then verifies TCP authentication before migration starts.
- Migration/runtime clients support either legacy DATABASE_URL or discrete PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD.
- Self-hosted Docker/Kubernetes manifests use discrete PG fields to avoid raw URL password interpolation.
- Runtime web uses providers_portal_app; production web is scrubbed of admin DB password variables.
- Example env files contain placeholders only; credential-like examples are rejected fail-closed.
